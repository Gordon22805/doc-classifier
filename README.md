# Support Ticket Classifier & Router

Небольшой сервис, который берёт текст обращения в поддержку и отвечает, что с ним делать: какая это категория, какой интент, насколько срочно, как клиент настроен, в какой отдел отправить и насколько модель уверена.



## Business Problem

Обращения в поддержку валятся в одну кучу. Оплата, доставка, доступ к аккаунту, сбои приложения, возвраты. Чтобы передать тикет нужному отделу, оператор читает его руками и на ходу решает, что это, насколько срочно и насколько клиент злой.

На потоке это ломается в трёх местах.

**Клиент ждёт.** Пока обращение лежит и ждёт разбора, человек сидит без ответа.

**Тикеты уезжают не туда.** Обращение про возврат уходит в логистику, клиента перекидывают из отдела в отдел, он злится сильнее.

**Нет картины.** Руководитель не видит, какой отдел завален и какие темы растут. Данных нет, потому что типы обращений никто не размечает.

Сервис закрывает это одним запросом к LLM. На выходе получается структурированная запись, которую можно сразу положить в очередь отдела и посчитать по ней нагрузку.

## How It Works

1. Клиент отправляет текст в `POST /predict`.
2. Pydantic проверяет запрос: текст не пустой и не длиннее `MAX_TEXT_LENGTH`.
3. LLM-сервис собирает промпт: системная инструкция со списком допустимых значений плюс сам текст обращения.
4. Запрос уходит в OpenRouter с `response_format: json_object`.
5. Модель возвращает JSON: категория, интент, приоритет, тональность, уверенность.
6. Ответ валидируется. Категория должна быть из перечня, интент должен относиться именно к этой категории, уверенность должна попадать в 0..1.
7. Python определяет отдел по категории и собирает финальный ответ.

Отдельного запроса за тональностью нет. Всё приходит одним ответом, поэтому на один тикет тратится один вызов модели.

Отдел никогда не берётся из текста, который написала модель. Модель отвечает только за категорию, маршрутизация живёт в коде и не зависит от того, как LLM сформулировала ответ.

## Architecture

```
User
  ↓
FastAPI (POST /predict)
  ↓
LLM Service
  ↓
OpenRouter
  ↓
Structured JSON
  ↓
Pydantic Validation
  ↓
Routing
  ↓
API Response
```

Слои разделены намеренно, чтобы каждый можно было проверить и заменить отдельно.

| Слой | Файл | Ответственность |
|------|------|-----------------|
| API | `app/main.py` | HTTP-эндпоинты, коды ошибок |
| Схемы | `app/schemas.py` | Перечни значений и валидация |
| LLM | `app/llm_service.py` | HTTP-запрос к OpenRouter, разбор ответа |
| Классификатор | `app/classifier.py` | Связка LLM и маршрутизации |
| Маршрутизация | `app/routing.py` | Категория в отдел |
| Промпт | `app/prompts.py` | Системная инструкция для модели |
| Аналитика | `app/analytics.py` | Пакетная обработка и распределения |
| Конфиг | `app/config.py` | Настройки из `.env` |

## Classification Categories

Восемь категорий, у каждой свой фиксированный список интентов. Модель не может придумать новое значение: список уходит в промпт, а ответ проверяется по тем же перечням. Если модель написала что-то своё, клиент получит 502, а не мусор в базе.

| Категория | Интенты | Отдел |
|-----------|---------|-------|
| PAYMENT | DUPLICATE_CHARGE, FAILED_PAYMENT, UNKNOWN_CHARGE, PAYMENT_PENDING | BILLING |
| REFUND | REFUND_REQUEST, REFUND_PENDING, REFUND_REJECTED | BILLING |
| DELIVERY | LATE_DELIVERY, LOST_PACKAGE, WRONG_ADDRESS, DELIVERY_STATUS | LOGISTICS |
| ORDER | CREATE_ORDER, CANCEL_ORDER, MODIFY_ORDER, ORDER_STATUS | SALES_SUPPORT |
| ACCOUNT | PASSWORD_RESET, ACCOUNT_LOCKED, LOGIN_PROBLEM, CHANGE_PERSONAL_DATA | ACCOUNT_SUPPORT |
| TECHNICAL | APP_ERROR, WEBSITE_ERROR, FEATURE_NOT_WORKING | TECH_SUPPORT |
| SUBSCRIPTION | CANCEL_SUBSCRIPTION, SUBSCRIPTION_PAYMENT, SUBSCRIPTION_PROBLEM | CUSTOMER_SUCCESS |
| OTHER | OTHER | GENERAL_SUPPORT |

Приоритеты: `LOW`, `MEDIUM`, `HIGH`, `URGENT`. Правила прописаны в промпте: правка данных профиля это LOW, не могу войти это MEDIUM, двойное списание это HIGH, крупная сумма без согласия клиента это URGENT.

Тональность: `POSITIVE`, `NEUTRAL`, `NEGATIVE`. Считается в том же запросе, отдельного вызова нет.

## LLM Integration

Запрос идёт на `{OPENROUTER_BASE_URL}/chat/completions` с заголовком `Authorization: Bearer`. Формат совместим с OpenAI Chat Completions, поэтому провайдера можно поменять, не трогая код.

Что делает интеграция:

- отправляет `response_format: {"type": "json_object"}`, чтобы модель отвечала JSON, а не прозой вокруг него;
- держит `temperature: 0`, чтобы ответы были воспроизводимыми;
- снимает markdown-обёртку, если модель всё-таки засунула JSON в тройные обратные кавычки;
- отдельно различает отказ по ключу, таймаут и битый ответ;
- при ошибке валидации говорит, какое именно поле не подошло.

Класс `LLMService` принимает готовый `httpx` транспорт, поэтому тесты гоняют настоящий путь запроса без сети и без ключа.

## API

### `GET /health`

```json
{"status": "ok"}
```

### `POST /predict`

Запрос:

```json
{"text": "С меня дважды списали деньги за одну покупку"}
```

Ответ:

```json
{
  "category": "PAYMENT",
  "intent": "DUPLICATE_CHARGE",
  "priority": "HIGH",
  "sentiment": "NEGATIVE",
  "confidence": 0.93,
  "department": "BILLING"
}
```

### `POST /analyze`

Берёт обращения из `data/sample_tickets.csv`, классифицирует каждое ровно один раз и возвращает распределения. Параметр `limit` ограничивает выборку, сверху его подрезает `MAX_TICKETS`.

Смотреть сервис удобнее всего через Swagger на `/docs`. Открыть `POST /predict`, нажать Try it out, вставить своё обращение, Execute. Этого хватает, чтобы увидеть всю цепочку вживую.

## Example

Запрос по двойному списанию:

```bash
curl -X POST http://127.0.0.1:8000/predict \
  -H "Content-Type: application/json" \
  -d "{\"text\": \"С меня дважды списали деньги за одну покупку\"}"
```

Ещё несколько обращений, на которых удобно проверить качество:

| Обращение | Ожидаемый результат |
|-----------|---------------------|
| Моя посылка должна была приехать вчера, но до сих пор её нет | DELIVERY / LATE_DELIVERY / LOGISTICS |
| Я забыл пароль и не могу войти | ACCOUNT / PASSWORD_RESET / ACCOUNT_SUPPORT |
| Приложение постоянно закрывается после запуска | TECHNICAL / APP_ERROR / TECH_SUPPORT |
| Я оформил возврат, но деньги так и не пришли | REFUND / REFUND_PENDING / BILLING |
| Списали крупную сумму, я этого не делал | PAYMENT / UNKNOWN_CHARGE / URGENT / BILLING |

Ответы нигде не захардкожены. Каждое обращение реально уходит в модель.

## Error Handling

Все ошибки уходят клиенту как `HTTPException` с внятным текстом. Необработанные исключения ловятся на уровне приложения и превращаются в 500 без трассировки в ответе: наружу не должно утекать внутреннее устройство.

| Ситуация | Код | Что видит клиент |
|----------|-----|------------------|
| Пустой текст | 422 | Текст обращения пуст |
| Текст длиннее лимита | 422 | Текст длиннее N символов |
| Не заданы ключ, URL или модель | 503 | OpenRouter не настроен |
| Ключ отклонён провайдером | 503 | OpenRouter отклонил ключ |
| Провайдер не ответил вовремя | 504 | OpenRouter не ответил за отведённое время |
| Провайдер вернул ошибку | 502 | OpenRouter вернул HTTP N |
| Модель вернула не JSON | 502 | Модель вернула не JSON |
| Неизвестная категория или плохая уверенность | 502 | Некорректное поле category: ... |

Валидация идёт снизу вверх. Сначала форма ответа, потом перечни значений, потом связка интента с категорией. Ответ, который не прошёл проверку, до бизнес-логики не доходит.

Логи пишутся на уровне INFO: факт запроса, категория и интент результата, время ответа модели, ошибки провайдера. Ключ в лог не попадает, полный текст обращения тоже.

## Analytics

Модуль `app/analytics.py` считает распределения по реальным результатам классификации, а не по заранее заготовленным числам:

- распределение по категориям;
- распределение по приоритетам;
- нагрузка по отделам;
- распределение по тональности.

Каждый тикет уходит в модель один раз, результат переиспользуется для всех четырёх срезов. Параллельность держит семафор, по умолчанию четыре одновременных запроса. Если отдельное обращение упало, прогон не разваливается: отказ попадает в `failed` и `failures`, остальные результаты считаются.

Запуск на демонстрационном наборе из тридцати обращений:

```bash
curl -X POST "http://127.0.0.1:8000/analyze?limit=30"
```

## Configuration

Настройки читаются из `.env`. Файл лежит в `.gitignore` и в репозиторий не попадает.

```bash
cp .env.example .env      # Windows PowerShell: copy .env.example .env
```

Обязательные параметры:

```env
OPENROUTER_API_KEY=ваш-ключ
OPENROUTER_BASE_URL=https://openrouter.ai/api/v1
LLM_MODEL=nvidia/nemotron-3.5-lightning:free
```

`OPENROUTER_BASE_URL` указывается до `/chat/completions`, без слэша на конце. Адрес и модель уже стоят по умолчанию в `app/config.py`, так что руками вписывать нужно только ключ. Имя модели берётся из списка OpenRouter: сервис не привязан к конкретной, значение уходит в запрос как есть.

Ключ бесплатный: https://openrouter.ai/keys

Необязательные параметры:

| Параметр | По умолчанию | Назначение |
|----------|--------------|------------|
| `LLM_TIMEOUT_SECONDS` | 30 | Таймаут запроса к провайдеру |
| `LLM_TEMPERATURE` | 0 | Температура модели |
| `MAX_TEXT_LENGTH` | 4000 | Максимальная длина обращения |
| `MAX_TICKETS` | 50 | Верхняя граница выборки для `/analyze` |

Если ключ, URL или модель не заданы, сервис всё равно запустится, но `POST /predict` ответит 503 и скажет, чего не хватает.

## Testing

```bash
py -m pytest
```

Тридцать семь тестов. Настоящих запросов к провайдеру нет.

| Файл | Что проверяет |
|------|---------------|
| `test_routing.py` | Все восемь категорий, регистр, неизвестное значение |
| `test_schemas.py` | Неизвестная категория, приоритет, тональность, уверенность вне диапазона, интент не из своей категории |
| `test_llm_service.py` | Состав запроса, заголовок авторизации, отказ по ключу, таймаут, не JSON, JSON в markdown, неожиданная структура |
| `test_api.py` | `/health`, полный ответ `/predict`, пустой и слишком длинный текст, коды 503, 504, 502 |

LLM в тестах подменяется: `test_llm_service.py` работает через `httpx.MockTransport`, `test_api.py` подменяет метод классификатора. Сеть не нужна, ключ тоже.

## Tech Stack

- **Python 3.10+**
- **FastAPI** для HTTP-слоя и автоматического Swagger
- **Pydantic v2** для перечней значений и валидации
- **httpx** для асинхронных запросов к OpenRouter
- **pydantic-settings** и **python-dotenv** для конфигурации из `.env`
- **pytest** и **pytest-asyncio** для тестов

Базы данных, Docker, брокера сообщений и фреймворков для агентов здесь нет намеренно. Задача решается одним сервисом и одним вызовом LLM на обращение. Всё остальное было бы инфраструктурой ради инфраструктуры.
