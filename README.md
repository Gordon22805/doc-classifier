# Support Ticket Classifier & Router

Сервис принимает текст обращения в поддержку и возвращает готовую маршрутизацию: категорию, интент, приоритет, тональность, отдел и уверенность модели.

Классификацию выполняет LLM через Groq (OpenAI-совместимый API), ответ валидируется Pydantic, распределение по отделам считает обычный Python по словарю.

## Business Problem

Обращения в поддержку приходят одним потоком: оплата, доставка, доступ к аккаунту, сбои приложения, возвраты. Чтобы передать обращение нужному отделу, оператор читает его вручную и определяет категорию, срочность и настроение клиента.

На потоке это даёт три проблемы:

- **Время до ответа.** Пока обращение ждёт разбора, клиент ждёт вместе с ним.
- **Ошибки маршрутизации.** Обращение про возврат уходит в логистику, клиента перекидывают между отделами.
- **Нет статистики.** Руководитель не знает, какой отдел перегружен и какие темы растут.

Сервис решает это одним запросом к LLM: обращение превращается в структурированную запись, которую можно сразу положить в очередь отдела и посчитать по ней нагрузку.

## How It Works

1. Клиент отправляет текст обращения в `POST /predict`.
2. Pydantic проверяет запрос: текст не пустой и не длиннее `MAX_TEXT_LENGTH`.
3. LLM-сервис собирает промпт: системная инструкция со списком допустимых значений плюс сам текст.
4. Запрос уходит в Groq с `response_format: json_object`.
5. Модель возвращает JSON с категорией, интентом, приоритетом, тональностью и уверенностью.
6. Ответ проходит валидацию: категория из перечня, интент относится к этой категории, уверенность в диапазоне 0..1.
7. Python определяет отдел по категории и собирает финальный ответ.

Отдел никогда не берётся из текста, который написала модель. Модель отвечает только за категорию, маршрутизация остаётся в коде и не зависит от формулировок LLM.

## Architecture

```
User
  ↓
FastAPI (POST /predict)
  ↓
LLM Service
  ↓
Groq
  ↓
Structured JSON
  ↓
Pydantic Validation
  ↓
Routing
  ↓
API Response
```

Слои намеренно разделены:

| Слой | Файл | Ответственность |
|------|------|-----------------|
| API | `app/main.py` | HTTP-эндпоинты, коды ошибок |
| Схемы | `app/schemas.py` | Перечни значений и валидация |
| LLM | `app/llm_service.py` | HTTP-запрос к Groq, разбор ответа |
| Классификатор | `app/classifier.py` | Связка LLM и маршрутизации |
| Маршрутизация | `app/routing.py` | Категория в отдел |
| Промпт | `app/prompts.py` | Системная инструкция для модели |
| Аналитика | `app/analytics.py` | Пакетная обработка и распределения |
| Конфиг | `app/config.py` | Настройки из `.env` |

## Classification Categories

Восемь категорий, для каждой фиксированный список интентов. Модель не может придумать новое значение: список попадает в промпт, а ответ проверяется по тем же перечням.

| Категория | Интенты | Отдел |
|-----------|---------|-------|
| PAYMENT | DUPLICATE_CHARGE, FAILED_PAYMENT, UNKNOWN_CHARGE, PAYMENT_PENDING | BILLING |
| REFUND | REFUND_REQUEST, REFUND_PENDING, REFUND_REJECTED | BILLING |
| DELIVERY | LATE_DELIVERY, LOST_PACKAGE, WRONG_ADDRESS, DELIVERY_STATUS | LOGISTICS |
| ORDER | CREATE_ORDER, CANCEL_ORDER, MODIFY_ORDER, ORDER_STATUS | SALES_SUPPORT |
| ACCOUNT | PASSWORD_RESET, ACCOUNT_LOCKED, LOGIN_PROBLEM, CHANGE_PERSONAL_DATA | ACCOUNT_SUPPORT |
| TECHNICAL | APP_ERROR, WEBSITE_ERROR, FEATURE_NOT_WORKING | TECH_SUPPORT |
| SUBSCRIPTION | CANCEL_SUBSCRIPTION, SUBSCRIPTION_PAYMENT, SUBSCRIPTION_PROBLEM | CUSTOMER_SUCCESS |
| OTHER | OTHER | GENERAL_SUPPORT |

Приоритеты: `LOW`, `MEDIUM`, `HIGH`, `URGENT`. Правила заданы в промпте: изменение данных профиля это LOW, невозможность войти это MEDIUM, двойное списание это HIGH, крупная сумма без согласия клиента это URGENT.

Тональность: `POSITIVE`, `NEUTRAL`, `NEGATIVE`. Определяется в том же запросе к LLM, отдельного вызова нет.

## LLM Integration

Запрос идёт на `{GROQ_BASE_URL}/chat/completions` с заголовком `Authorization: Bearer`. Формат совместим с OpenAI Chat Completions, поэтому провайдера можно заменить, не меняя код.

Что делает интеграция:

- отправляет `response_format: {"type": "json_object"}`, чтобы модель отвечала JSON, а не текстом;
- требует `temperature: 0` для воспроизводимости;
- снимает markdown-обёртку, если модель всё же обернула JSON в тройные кавычки;
- отдельно обрабатывает отказ по ключу, таймаут и битый ответ;
- при ошибке валидации сообщает, какое именно поле не подошло.

Класс `LLMService` принимает готовый `httpx` транспорт, поэтому тесты проверяют реальные запросы без сети и без ключа.

## API

### `GET /health`

```json
{"status": "ok"}
```

### `POST /predict`

Запрос:

```json
{"text": "С меня дважды списали деньги за одну покупку"}
```

Ответ:

```json
{
  "category": "PAYMENT",
  "intent": "DUPLICATE_CHARGE",
  "priority": "HIGH",
  "sentiment": "NEGATIVE",
  "confidence": 0.93,
  "department": "BILLING"
}
```

### `POST /analyze`

Берёт обращения из `data/sample_tickets.csv`, классифицирует каждое ровно один раз и возвращает распределения. Параметр `limit` ограничивает размер выборки, сверху его ограничивает `MAX_TICKETS`.

Swagger доступен на `/docs`. Это основной способ посмотреть сервис: открыть `POST /predict`, нажать Try it out, вставить текст своего обращения и получить разбор.

## Example

Запрос по двойному списанию:

```bash
curl -X POST http://127.0.0.1:8000/predict \
  -H "Content-Type: application/json" \
  -d "{\"text\": \"С меня дважды списали деньги за одну покупку\"}"
```

Ещё несколько обращений, на которых удобно проверить качество:

| Обращение | Ожидаемый результат |
|-----------|---------------------|
| Моя посылка должна была приехать вчера, но до сих пор её нет | DELIVERY / LATE_DELIVERY / LOGISTICS |
| Я забыл пароль и не могу войти | ACCOUNT / PASSWORD_RESET / ACCOUNT_SUPPORT |
| Приложение постоянно закрывается после запуска | TECHNICAL / APP_ERROR / TECH_SUPPORT |
| Я оформил возврат, но деньги так и не пришли | REFUND / REFUND_PENDING / BILLING |
| Списали крупную сумму, я этого не делал | PAYMENT / UNKNOWN_CHARGE / URGENT / BILLING |

Ответы не захардкожены: каждое обращение реально уходит в модель.

## Error Handling

Все ошибки возвращаются как `HTTPException` с понятным текстом. Необработанные исключения перехватываются на уровне приложения и превращаются в 500 без трассировки в ответе.

| Ситуация | Код | Что видит клиент |
|----------|-----|------------------|
| Пустой текст | 422 | Текст обращения пуст |
| Текст длиннее лимита | 422 | Текст длиннее N символов |
| Не заданы ключ, URL или модель | 503 | Groq не настроен |
| Ключ отклонён провайдером | 503 | Groq отклонил ключ |
| Провайдер не ответил вовремя | 504 | Groq не ответил за отведённое время |
| Провайдер вернул ошибку | 502 | Groq вернул HTTP N |
| Модель вернула не JSON | 502 | Модель вернула не JSON |
| Неизвестная категория или плохая уверенность | 502 | Некорректное поле category: ... |

Валидация снизу вверх: сначала проверяется форма ответа, затем перечни значений, затем связка интента с категорией. Ответ, который не прошёл проверку, до бизнес-логики не доходит.

Логи пишутся на уровне INFO: факт запроса, категория и интент результата, время ответа модели, ошибки провайдера. Ключ в логи не попадает, полный текст обращения тоже.

## Analytics

Модуль `app/analytics.py` считает распределения по реальным результатам классификации, а не по заранее заданным значениям:

- распределение по категориям;
- распределение по приоритетам;
- нагрузка по отделам;
- распределение по тональности.

Каждый тикет уходит в LLM один раз, результат переиспользуется для всех четырёх срезов. Параллельность ограничена семафором, по умолчанию четыре одновременных запроса. Отказы отдельных обращений не роняют весь прогон: они попадают в `failed` и `failures`, остальные результаты считаются.

Запуск на демонстрационном наборе из тридцати обращений:

```bash
curl -X POST "http://127.0.0.1:8000/analyze?limit=30"
```

## Configuration

Настройки читаются из `.env`. Файл в `.gitignore` и в репозиторий не попадает.

```bash
cp .env.example .env      # Windows PowerShell: copy .env.example .env
```

Обязательные параметры:

```env
GROQ_API_KEY=ваш-ключ
GROQ_BASE_URL=https://api.groq.com/openai/v1
LLM_MODEL=llama-3.3-70b-versatile
```

`GROQ_BASE_URL` указывается до `/chat/completions`, без слэша на конце. Адрес и модель уже подставлены по умолчанию в `app/config.py`, поэтому обязателен только ключ. Имя модели берётся из списка Groq: сервис не привязан к конкретной модели, значение подставляется в запрос как есть.

Ключ выдаётся бесплатно: https://console.groq.com/keys

Необязательные параметры:

| Параметр | По умолчанию | Назначение |
|----------|--------------|------------|
| `LLM_TIMEOUT_SECONDS` | 30 | Таймаут запроса к провайдеру |
| `LLM_TEMPERATURE` | 0 | Температура модели |
| `MAX_TEXT_LENGTH` | 4000 | Максимальная длина обращения |
| `MAX_TICKETS` | 50 | Верхняя граница выборки для `/analyze` |

Если ключ, URL или модель не заданы, сервис запускается, но `POST /predict` отвечает 503 с объяснением, чего не хватает.

## Testing

```bash
py -m pytest
```

Тридцать семь тестов, реальные запросы к провайдеру не выполняются.

| Файл | Что проверяет |
|------|---------------|
| `test_routing.py` | Все восемь категорий, регистр, неизвестное значение |
| `test_schemas.py` | Неизвестная категория, приоритет, тональность, уверенность вне диапазона, интент не из своей категории |
| `test_llm_service.py` | Состав запроса, заголовок авторизации, отказ по ключу, таймаут, не JSON, JSON в markdown, неожиданная структура |
| `test_api.py` | `/health`, полный ответ `/predict`, пустой и слишком длинный текст, коды 503, 504, 502 |

LLM в тестах подменяется: `test_llm_service.py` работает через `httpx.MockTransport`, `test_api.py` подменяет метод классификатора. Сеть не нужна.

## Tech Stack

- **Python 3.10+**
- **FastAPI** для HTTP-слоя и автоматического Swagger
- **Pydantic v2** для перечней значений и валидации
- **httpx** для асинхронных запросов к Groq
- **pydantic-settings** и **python-dotenv** для конфигурации из `.env`
- **pytest** и **pytest-asyncio** для тестов

База данных, Docker, брокер сообщений и фреймворки для агентов не используются намеренно: задача решается одним сервисом и одним вызовом LLM на обращение.
